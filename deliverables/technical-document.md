# 议场 AGORA 技术文档

多 Agent 协同工作流看板 · 全国高校 Vibe Coding 开发挑战赛参赛作品

> 本文档为 PDF 导出源稿，目标页数不超过 30 页。配套材料见仓库 `docs/`、`prompts/`、`demo/`。文中所述能力均可在仓库中核验；尚未完成的生产能力在“边界与局限”一节明确说明，不冒充已实现。

---

## 1. 作品概述

### 1.1 一句话定位

议场 AGORA 是一个面向高校大创、创新创业和跨专业学生团队的多 Agent 协同工作流看板。它把一个模糊的项目议题拆成“需求澄清—方案拆解—风险质询—公平合规—行动决议”五个职责明确的协作节点，产出一份包含负责人、验收指标和保留异议的可回放决议。

### 1.2 选题方向

- 主方向：方向 1「多 Agent 协同工作流看板」
- 辅助方向：方向 7「数字孪生与轻量仿真」——把真实团队的协作状态映射为可观察的数字工作流

### 1.3 核心用户

| 用户 | 需求 |
|---|---|
| 大创/竞赛项目负责人 | 把讨论转成可交付任务 |
| 跨专业学生成员 | 明确自己的职责和交付物 |
| 指导教师 | 快速了解风险和待确认事项 |
| 项目评审者 | 查看决策证据链和异议 |

## 2. 真实痛点与解题有效性

### 2.1 痛点

校园创新团队协作中普遍存在四个问题：

1. 需求漂移：成员对目标理解不一致，讨论无法收敛；
2. 观点堆叠：会议产生大量意见，但没有结构化工作节点；
3. 风险后置：隐私、公平、责任边界常在事后才被发现；
4. 无责任链：会后没有负责人、截止时间和验收指标。

### 2.2 为什么普通聊天机器人无效

普通聊天机器人只会把“会议记录”换成“AI 文案”。议场要求：

- 每个角色只产出一类工作卡；
- 下一节点只能消费上一节点已确认的结果；
- 冲突必须被记录、分级和处理；
- 决议必须包含负责人和验收指标；
- 过程必须可回放。

### 2.3 产品闭环

```text
创建议题 → 需求洞察 → 工作流拆解 → 风险质询 → 公平合规检查 → 行动决议 → 演进回放
```

## 3. 五个 Agent 的职责边界（意图控制的核心）

| Agent | 角色 | 核心问题 | 必须产出 | 明确不负责 |
|---|---|---|---|---|
| 闻野 | 需求洞察员 | 谁在什么场景遇到什么损失 | 需求卡、事实、待验证假设 | 不设计方案、不伪造事实 |
| 墨衡 | 工作流架构师 | 如何拆成可协作节点 | 工作流卡、输入输出、验收条件 | 不判断风险可接受度 |
| 秋序 | 风险质询员 | 最可能在哪一步失败 | 风险卡、反例、失败条件 | 不做无依据否定 |
| 衡山 | 公平与合规官 | 谁被忽略、责任在哪 | 合规卡、脱敏/撤回/人审要求 | 不替团队做商业取舍 |
| 太史 | 项目统筹官 | 能否进入下一节点 | 决议卡、负责人、期限、指标、异议 | 不删除未解决分歧 |

角色间存在依赖顺序，防止“五个聊天机器人轮流说话”：

```text
需求卡 → 工作流卡 → 风险卡 / 合规卡 → 行动决议卡
```

## 4. 意图控制策略

### 4.1 Prompt 设计原则

1. 先定义问题和边界，再写代码；
2. 每轮 Prompt 只要求一个明确产出，避免一次生成大量不可审查代码；
3. 明确禁止项（禁止 `any`、禁止随机数、禁止外部 API）；
4. 要求结构化输出（证据类型、置信度、冲突状态）；
5. 要求补充自动化测试而不是只靠手工点击；
6. 发现偏差后，用“验收标准 + 复现条件”引导 AI 修复。

### 4.2 人类与 AI 的分工

| 环节 | 人类负责 | AI 负责 |
|---|---|---|
| 问题定义 | 痛点、用户、边界 | 拆解、追问、补全 |
| 架构 | 分层、数据流、约束 | 生成代码、补测试 |
| 验收 | 标准、复现条件 | 实现与自检 |
| 风险 | 不可逆动作判断 | 列举风险和反例 |
| 最终决策 | 确认与承诺 | 只提建议 |

### 4.3 结构化输出约束

消息至少包含 `agentId`、`phase`、`text`、`evidence[]`；证据必须标记为事实、假设、风险或提案，并带置信度。决议必须包含行动建议、理由、异议和下一步。业务层不接受自由散文作为最终状态。

### 4.4 可逆推进

产品遵循“建议而非自动执行、时间盒试点而非直接承诺、可撤回而非不可逆”。

## 5. 架构设计

### 5.1 分层

```text
视图层         src/components        页面与交互
HTTP/SSE 层    src/app/api           健康检查、房间、编排接口
应用编排层     src/application       输入规范化、事件顺序、冲突治理
领域层         src/domain            Agent、证据、冲突、工作流、房间、决议
基础设施层     src/infrastructure    Provider 边界、房间快照与事件仓储
运行编排       scripts               开发、健康检查、验证、材料检查
```

约束：领域层不依赖 React、HTTP、文件系统或具体模型；Provider 可替换；UI 不直接拼装模型结果。

### 5.2 接口

| 接口 | 作用 |
|---|---|
| `GET /api/health` | 服务、Provider、存储、版本和检查时间 |
| `POST /api/rooms` | 创建议题房间并落盘事件 |
| `GET /api/rooms/:roomId` | 读取房间快照与事件 |
| `POST /api/deliberate` | SSE 流式编排事件 |

### 5.3 事件模型

```text
run.started → workflow.created → message.created
→ conflict.detected → conflict.contained
→ decision.ready → run.completed
```

### 5.4 数据流

```text
用户输入 → 输入规范化 → 场景透镜推导
→ Agent 结构化产出 → 冲突分级与处置
→ 决议生成 → 事件落盘 → 回放渲染
```

### 5.5 状态管理

- 前端：单一议题状态与消息列表；
- 后端：房间快照 + 追加事件，原子写入临时文件后替换；
- 演示模式：确定性 Mock，不依赖网络与 API Key。

### 5.6 冲突治理

冲突是正常业务事件。每个冲突记录类型、强度、责任人、证据、状态、处置方案和是否阻塞不可逆执行：

| 类型 | 处置 |
|---|---|
| 证据冲突 | 补充来源与置信度，不把假设当事实 |
| 范围冲突 | 拆成两个工作节点 |
| 风险冲突 | 时间盒试点，用失败指标验证 |
| 责任/合规冲突 | 待人工确认；禁止不可逆执行，但继续生成草案 |

因此 Agent 意见不一致不会导致系统停止。

## 6. 可复现性论证

### 6.1 一命令复现

```bash
npm install
npm run dev
```

打开 `http://localhost:3000`；无 `.env.local`、无 API Key、无网络均可完成演示。

### 6.2 确定性设计

- 无 `Math.random()`；
- 同一 `topic + context` 得到同一业务文本；
- 不同输入在用户、风险、试点、指标上产生实质差异；
- 事件 ID 由输入摘要与事件序号稳定生成，不使用当前时间；
- 运行时间戳仅作为审计信息。

### 6.3 场景透镜

`topic + context` 推导场景透镜，覆盖校园节能、教学课程、就业服务、公共服务和通用创新项目，五个 Agent 消费同一透镜，避免各自为政地解释输入。

### 6.4 自动化验证

`npm run typecheck`、`npm test`、`npm run build`、`npm run contest:verify` 均可本地执行；测试覆盖同输入稳定、不同输入差异、交叉质询消费主题、决议消费主题、事件 ID 稳定、冲突治理与房间生命周期。

### 6.5 事件回放

每次运行产生有序事件，可在页面回放；事件可落盘为 JSON，后续可替换为 SQLite/PostgreSQL 而不改渲染模型。

## 7. 工程质量

- TypeScript strict，`noUncheckedIndexedAccess`；
- 不使用 `any` 绕过类型问题；
- 领域层纯函数并带单元测试；
- 房间落盘采用原子写入；
- 环境变量模板不含密钥；
- 健康检查返回可观测状态；
- 生产构建通过。

---

## 8. 边界与局限

当前为比赛级可运行 MVP，以下能力明确尚未实现，不作为已完成能力宣传：

- 用户认证与 RBAC；
- 多用户并发协作与锁；
- PostgreSQL 正式仓储；
- 模型输出 JSON Schema 校验；
- Provider 重试、熔断、配额与审计；
- 敏感信息删除流程；
- 房间分享权限；
- 真实用户指标看板。

## 9. 原创性声明

本作品为本次竞赛从零设计，未复制既有开源项目业务代码或视觉页面；仅吸收实习期间形成的通用工程经验（根命令编排、健康检查、分层、环境隔离），未使用实习项目的业务代码、接口、数据、配置或视觉资源。对比记录见 `docs/enterprise-comparison.md` 与 `docs/architecture-boundary.md`。
