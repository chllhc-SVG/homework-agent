# 实习工程经验与议场 AGORA 的深度对比

## 1. 对比目的

`xiaoke-project` 是一个面向多服务、容器、数字人和 MCP 能力的工程编排工作区；议场 AGORA 是一个面向高校创新团队的多 Agent 协同工作流产品。两者不属于同一业务，不能通过复制代码得到另一个系统。本文件只说明“通用工程方法如何被重新设计并落地到本作品”。

## 2. 架构方法对照

| 实习项目中的通用经验 | 议场 AGORA 的独立落地 | 为什么不是照搬 |
|---|---|---|
| 根目录统一命令，减少新人记忆成本 | `scripts/agora.mjs` 统一开发、健康检查、工程验证和比赛材料检查 | 命令对象从 Docker/数字人切换为 Next.js/议题房间/评审材料 |
| 多服务启动前做 health 检查 | `/api/health` 返回 Provider、存储方式、版本和检查时间 | 检查对象是议题服务，不访问实习项目端口和内部服务 |
| 环境变量控制开发和真实服务 | `AGORA_ENGINE`、`AGORA_DATA_DIR`、LLM 配置控制 Mock/Live/数据目录 | 配置名、数据流和 Provider 边界完全重新设计 |
| 子系统通过编排脚本统一启动 | `src/application` 负责工作流，`src/infrastructure` 负责房间事件文件 | 不使用 compose、MCP、Electron 或公司服务代码 |
| 服务异常要能诊断 | 房间状态、事件序列、冲突记录、错误响应和回放 | 诊断对象变成协作过程和决策审计链 |
| 开发环境与生产配置分离 | Mock 免 Key 演示、Live Provider 可选、JSON 事件日志可替换 | 面向比赛复现和校园项目试点，不复用原项目配置 |

## 3. 议场的企业化边界

### 3.1 领域层

领域层定义 Agent、证据、冲突、工作流、决议和房间生命周期。它不依赖 React、文件系统或 HTTP，便于测试和未来接入数据库。

### 3.2 应用层

应用层负责：

- 输入规范化；
- 工作流阶段顺序；
- Agent 事件编排；
- 冲突治理；
- 决议生成；
- Provider 选择。

### 3.3 基础设施层

基础设施层目前提供：

- JSON 房间快照；
- JSON 事件追加；
- 原子写入临时文件后替换；
- 房间 ID 校验；
- 后续替换 SQLite/PostgreSQL 的接口边界。

### 3.4 接口层

当前接口：

```text
GET  /api/health
POST /api/rooms
GET  /api/rooms/:roomId
POST /api/deliberate
```

API 只承担请求、响应和 SSE 传输，不把业务规则塞进路由函数。

## 4. 从演示到落地的产品能力

当前版本已经具备可落地 MVP 的关键骨架：

- 一个议题对应一个房间；
- 房间有草稿、运行、待审查、已决议状态；
- 每个事件有序号和记录时间；
- 决议可以被回放和导出；
- 冲突不会让工作流中断；
- 责任/合规冲突会形成不可逆执行门禁；
- 默认 Mock 保证评审复现；
- Live Provider 可以在不改 UI 的情况下替换。

## 5. 还未冒充为生产能力的部分

当前版本仍是比赛级可运行 MVP，不宣称已经是生产系统。以下能力应在真实试点中继续建设：

- 用户认证和 RBAC；
- PostgreSQL/SQLite 正式仓储；
- 多用户协作和并发锁；
- 模型输出 JSON Schema 校验；
- Provider 重试、熔断、配额和审计；
- 敏感信息脱敏和删除请求；
- 房间分享权限；
- 指标看板和真实用户反馈。

这样既展示了企业化架构方向，也没有把尚未实现的生产能力包装成已经完成的功能。
