# 可复现开发与 Prompt 记录指南

## 重要说明

本文件是操作指南和 Prompt 模板，不是已经发生的 Cursor 原始对话。只有在 Cursor 中真实发送、真实得到回复、真实修改并完成验证后，才能把原始截图/导出文件归档为比赛证据。

## 一、什么叫“可复现”

可复现不是每次运行都返回一模一样的随机散文，而是满足四个条件：

1. 同一份代码、同一议题、同一背景、同一运行模式，能得到同一组结构化结果；
2. 不同议题或背景会进入不同的角色分析路径，而不是只替换标题；
3. 每次运行都有明确的事件顺序、角色、证据、冲突和决议；
4. 评委可以按 README 的命令启动，并通过输入复现演示链路。

当前 Mock 模式使用“输入驱动 + 确定性规则”：会根据节能、教学、就业、公共服务等主题词选择不同的分析透镜；同一输入的文字结果稳定，不同输入会出现不同用户、风险、试点和指标。事件时间戳属于运行审计信息，不作为业务文本一致性的判断依据。

## 二、新建 Cursor 对话的推荐流程

新建对话后，不要一上来只说“把项目做得更好”。按以下顺序发送，每次等待 Cursor 回复并完成验证，再进入下一条。

### 对话 1：提出问题并约束范围

```text
这是一个已经完成第一版的高校创新项目多 Agent 协同工作流看板。当前真实问题是：用户在“你想让议场讨论什么？”输入不同议题后，五个角色输出仍然刻板，交叉质询也基本固定，说明 Mock 编排没有真正消费 topic 和 context。

请先只做问题分析，不要立即修改代码。请检查：
1. createOpeningMessages 是否把 topic/context 只拼接到一处；
2. createDecision 是否固定返回同一议题；
3. 交叉质询是否写死；
4. Mock 模式如何在不依赖网络和 API Key 的情况下做到“输入驱动且确定性”；
5. 如何保证同一输入重复运行文本稳定、不同输入能体现不同用户/风险/试点/指标。

请给出最小但可维护的领域层改造方案，禁止使用 any，禁止引入随机数，先不要修改文件。
```

### 对话 2：让 Cursor 实现输入驱动规则

```text
按照刚才确认的方案实施，但严格保持领域层纯函数和现有 Agent 职责边界。

要求：
- 增加一个由 topic + context 推导的 DeliberationLens；
- 至少覆盖校园节能、教学课程、就业服务、公共服务和通用创新项目五类场景；
- 闻野必须输出当前场景的用户和证据问题；
- 墨衡必须输出当前场景的试点方式；
- 秋序必须质询当前场景的失败条件；
- 衡山必须输出当前场景的数据/责任边界；
- 太史的决议必须使用当前 topic，并生成当前场景的试点、指标和下一步；
- 同一输入的业务文本必须稳定，不同输入不能只替换标题；
- 保留 Mock 无网络复现能力。

请先修改 src/domain/deliberation.ts，再同步应用层和页面调用；修改后运行 npm run typecheck 和 npm test。
```

### 对话 3：引导 Cursor 修复验证问题

```text
请检查刚才的修改是否真正满足以下验收标准：
1. 两次输入完全相同的 topic/context，Agent 文本完全一致；
2. 输入“校园节能试点”与“课程反馈改进”，至少用户、风险、试点、指标有实质差异；
3. 交叉质询不能继续使用固定的“自动议价”或其他旧业务文案；
4. 决议书 issue、recommendation、nextSteps 必须来自当前输入；
5. 日期、事件时间戳可以变化，但不能影响业务文本的确定性。

请补充测试，不要只靠手工点击。测试至少覆盖：同输入稳定、不同输入不同、交叉质询消费当前主题、决议消费当前主题。若发现旧测试依赖旧业务文案，请同步更新为新的领域验收标准，并说明原因。
```

### 对话 4：进行真实浏览器验收

```text
请不要再修改代码，先给出一份浏览器验收清单。我会分别输入：
A. 如何做校园节能试点？
B. 如何改进课程反馈？
C. 如何建设校园就业服务？

每次都填写不同背景，记录五个 Agent 的第一条核心产出、交叉质询、冲突图谱和决议书变化。请告诉我截图应该分别截哪些区域，以及如何把结果和本轮 Git commit 对应起来。
```

## 三、每轮必须保存的证据

每一轮都要保存：

```text
01-我的Prompt.png
02-Cursor分析.png
03-Cursor修改文件.png
04-测试通过.png
05-浏览器输入与结果.png
06-Git提交记录.png
```

同时保存原始导出，不要只保存手工摘要：

```text
prompts/raw/迭代-输入驱动Mock-原始导出.html
prompts/raw/迭代-输入驱动Mock-脱敏版.md
```

## 四、Git 提交对应方式

本轮真实完成后再创建提交，提交信息应描述实际落地内容，例如：

```text
让 Mock 结果随议题和背景变化
```

提交正文建议说明：

```text
问题：不同议题得到固定 Agent 话术，无法证明输入真正进入编排。
处理：增加输入驱动的场景透镜、稳定规则和针对性测试。
验证：同输入稳定、不同输入有差异，类型检查和测试通过。
证据：prompts/raw/迭代-输入驱动Mock-原始导出.html
```

不要提前伪造 commit，也不要把一次真实对话拆成不存在的多轮对话。

## 六、最终判断标准

只有同时满足以下条件，才能在材料中写“本轮已完成”：

- Cursor 原始 Prompt 和回复已保存；
- 代码修改确实由该轮对话引导完成；
- Git 提交已经对应本轮功能；
- 自动化测试覆盖了核心行为；
- 浏览器中至少用两个不同议题验证过差异；
- 运行命令和结果已截图或录屏；
- 没有把模板内容冒充原始 AI 记录。
