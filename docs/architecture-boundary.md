# 架构借鉴边界与原创性说明

## 1. 借鉴的只是工程方法，不是业务实现

本作品的工程设计参考了参赛者在实习项目中形成的通用工程经验：

- 根目录统一命令入口，降低新成员启动成本；
- 服务启动前做健康检查；
- 将领域逻辑、应用编排、基础设施适配和视图层分开；
- 通过环境变量切换本地演示和真实服务；
- 关键过程保留可追踪的事件记录。

这些属于通用的软件工程方法，不包含实习项目的业务代码、公司数据、接口地址、视觉资源、私有提示词、用户数据或内部配置。

## 2. 本作品的独立设计

「议场 AGORA」围绕校园团队决策问题重新设计了自己的：

- 多 Agent 角色体系；
- 证据、假设、风险和提案的结构化模型；
- 交叉质询关系；
- 冲突图谱；
- 保留异议的决议书；
- 面向评审复现的演进回放；
- 无 Key 确定性 Mock Provider。

它与实习项目的业务目标、页面、数据模型和部署对象不同，不能通过复制实习项目代码直接得到本作品。

## 3. 分层约束

```text
视图层 src/components
    ↓ 只消费状态和领域结果
应用层 src/application
    ↓ 编排事件顺序、输入校验和 Provider 选择
领域层 src/domain
    ↓ 纯函数、类型和业务不变量
基础设施层 src/infrastructure
    ↓ 外部模型、环境变量和后续持久化适配
```

API 路由只负责 HTTP/SSE 适配，不直接拼装业务规则。这样可以在不改 UI 的情况下更换模型 Provider，也可以在不改领域层的情况下增加数据库或事件仓储。

## 5. 提交时的合规动作

- 不在仓库中提交实习项目源代码；
- 不提交公司名称以外的内部信息、域名、账号、密钥和数据；
- 不复制实习项目的 README、页面截图、接口定义或组件；
- 在技术文档中主动说明“借鉴通用工程方法，业务和实现独立”；
- 如评委要求说明来源，提供本文件和 Git 演进记录。
