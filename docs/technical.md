# 议场 AGORA 技术文档

## 1. 项目概述

议场 AGORA 面向高校大创、创新创业和跨专业项目团队，解决“需求漂移、讨论无结论、风险晚暴露、会后没人负责”的协作问题。它是一个多 Agent 协同工作流看板，不是普通聊天机器人：每个 Agent 只负责一类工作卡，上一节点的结构化结果才允许进入下一节点，最终形成负责人、截止时间、验收指标和保留异议的决议。

核心数据流为：

```text
议题卡 → 需求卡 → 工作流卡 → 风险卡 / 合规卡 → 行动决议卡 → 回放日志
```

## 2. 意图控制策略

### 2.1 角色约束

- **闻野·需求洞察员**：确认用户、场景、损失和证据，只提交需求卡，不直接给技术方案。
- **墨衡·工作流架构师**：把需求卡拆成阶段、输入、输出、依赖和验收条件，负责把愿景变成协作节点。
- **秋序·风险质询员**：寻找最可能失败的环节，提交反例、失败模式和压力测试问题，不做无依据否定。
- **衡山·公平与合规官**：检查脱敏、知情、撤回、申诉和人工确认边界，确保被影响者进入决策。
- **太史·项目统筹官**：汇总前四类工作卡，生成负责人、截止时间、验收指标和异议记录，不删除未解决分歧。

角色之间有顺序和依赖：太史不能跳过需求证据和风险/合规检查直接生成行动结论；墨衡不能替代闻野创造用户事实；秋序和衡山的输出必须保留在决议中。

### 2.2 结构化输出

业务层不接受自由散文作为最终状态。消息至少包含 `agentId`、`phase`、`text`、`evidence[]`；证据必须标记为事实、假设、风险或提案，并包含置信度。决议必须包含行动建议、理由、异议和下一步。

### 2.3 可逆推进

产品设计遵循“建议而非自动执行、先试点而非直接承诺、可撤回而非不可逆”的约束。这使 AI 的建议进入真实业务前先经过人类确认和可观测实验。

### 2.4 冲突治理规则

冲突是正常业务事件，不是系统异常。每个冲突都进入 `ConflictRecord`，至少记录：冲突类型、提出双方、强度、责任人、证据 ID、当前状态、处理方案和是否阻塞不可逆执行。

- 证据冲突：补充来源和置信度，暂不把假设写成事实；
- 范围冲突：拆成两个工作节点，分别定义输入、输出和通过条件；
- 风险冲突：采用时间盒试点，用失败指标验证，不用争论替代验证；
- 责任/合规冲突：保持“待人工确认”，系统仍生成可审查草案，但禁止进入不可逆执行。

因此，即使 Agent 观点不一致，编排流也不会崩溃：冲突被记录、分级、转化为验证任务或人工门禁，最终决议会保留异议。

## 3. 工作流与编排流

```text
intake    闻野：需求卡
   ↓
shape     墨衡：工作流卡
   ↓
challenge 秋序：风险卡
   +
safeguard 衡山：合规卡
   ↓
commit    太史：行动决议卡
```

每个阶段包含输入、输出、责任人和通过条件。应用层按固定顺序生成 `workflow.created`、`message.created`、`conflict.detected`、`conflict.contained`、`decision.ready`、`run.completed` 事件；评委可以按事件顺序回放完整过程。

## 4. 架构设计

- **View**：Next.js App Router + React 客户端组件，负责交互状态与可视化。
- **Application**：`src/application/deliberation-service.ts` 负责输入规范化、事件顺序和决议编排；`/api/deliberate` 只负责 HTTP/SSE 适配，发送 `run.started`、`message.created`、`decision.ready`、`run.completed` 事件。
- **Domain**：`src/domain` 的类型、角色、冲突关系和决议构造保持纯函数，独立于 React 和 Provider。
- **Infrastructure**：`src/infrastructure/provider.ts` 定义外部模型接入边界和 Mock/Live 选择规则，避免把密钥、网络请求和领域规则混在组件里。
- **运行编排**：`scripts/agora.mjs` 提供统一的开发、健康检查、工程验证和比赛材料检查入口，吸收通用的多服务项目启动经验但不复用实习项目代码。
- **Replay**：前端以事件消息为基础渲染演进回放，展示事件类型、时间和质询关系。

## 4. 工程质量

TypeScript strict 模式；领域层有单元测试；API 使用 SSE 流式反馈；环境变量模板不含密钥；真实 Provider 可选，默认零配置启动；决议明确保留异议，避免把模型输出包装成绝对正确。

## 5. 可复现性论证

在空环境中执行 `npm install && npm run dev` 即可启动。Mock 模式不依赖网络、不依赖数据库、不依赖 API Key。核心函数 `createOpeningMessages`、`createConflicts`、`createDecision` 的输入输出稳定，并由测试覆盖。每一次交互事件都具有明确类型，后续可落盘到 JSONL 或数据库而不改变渲染模型。

## 6. 局限与后续

当前演示版本使用内存状态，刷新页面后房间不会持久化；正式决赛版本应增加 JSONL/SQLite 事件仓储、房间分享链接、脱敏数据集、真实 Provider 的超时与重试、模型输出 schema 校验，以及多用户权限控制。这些约束已纳入路线图，不以演示数据冒充真实生产能力。
